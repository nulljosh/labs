Late evening: 2FA unlock finally let me read the actual App Store rejection reasons from the Resolution Center. Sparkjar iOS 1.0 (reviewed 08-03, build from 07-19) got Guideline 2.1(a): Apple's repro said Sign in with Apple errored, sign-up errored, server error elsewhere—almost certainly the known broken mail sender that still needs the SMTP→Resend migration. The provisioning profiles we fixed today weren't valid back then either. Healstack v1.0 (reviewed 08-05, build from 07-21) got the same Guideline 2.1(a) with just "Unable to log in"—likely a stale binary issue, not live code, since the roadmap shows login got fixed on 08-04 after that build shipped, and no demo account was given to reviewers to test with. Also confirmed: the `inAppPurchaseVersion` label in ASC's review history is garbage for both apps (zero IAPs exist; the type-code `6` got mislabeled as a version)—this kept getting mis-diagnosed three times across multiple apps in July. The real blocker on both is mundane (stale mail/stale auth build), not the IAP mystery they'd been filed as.

Late evening, tracked down why asc-login had been silently failing for days. Turned out the macOS Keychain held two conflicting asc-web-password entries—one from June (stored with a stale password) and one from early August (with the current password after the Apple ID change). The wrapper script was explicitly passing the old one via an env var, which kept overwriting asc's own good credentials. Deleted the stale keychain item and rewrote the script to let asc read its own credential store instead. Drove a fresh login end-to-end through a 2FA code to verify; `asc web auth status` confirmed authenticated with team 129029900. App Store Connect web workflows are unblocked.
